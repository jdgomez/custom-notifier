## Context

`:domain` is pure Kotlin (no Android) and holds `Product` with `Stock` (exact `Quantity` as a reduced `BigInteger` fraction plus the `Instant` it was recorded at), `Rule` and the value types. `:app` is a Compose app with a placeholder screen and no `Application` class. ADR 0006 mandates SQLite in private storage with parameterized queries; ADR 0010 asks for a minimal footprint; ADR 0012 asks for ports and adapters. Requirements are in `specs/`; motivation in `proposal.md`.

## Goals / Non-Goals

**Goals:**
- A domain port that the later UI, notification and calendar changes use without knowing about Room.
- Lossless storage of every domain value.
- Tests of the adapter on the JVM (`./gradlew test`), no emulator.

**Non-Goals:**
- Migrations (none in v1), a separate data module, a DI framework.

## Decisions

### Identity generated in the domain
`ProductId` is a value class over `java.util.UUID`, generated by `Product.create` (`UUID.randomUUID()`), and is the first property of `Product`. Edits keep it because they `copy` the product. Stored as the UUID's canonical text in a `TEXT PRIMARY KEY` column.

Alternative considered: an auto-increment `Long` from SQLite. Rejected: a product would have no identity until saved, the domain would depend on the database to create one, and ids would be reused-looking integers across reinstalls.

### The port lives in the domain and uses coroutines
```
interface ProductRepository {
    fun observeAll(): Flow<List<Product>>
    suspend fun find(id: ProductId): Product?
    suspend fun save(product: Product)
    suspend fun delete(id: ProductId)
}
```
`kotlinx-coroutines-core` is pure Kotlin, so `:domain` stays free of Android. Alternative considered: blocking functions. Rejected: every caller would have to move work off the main thread by hand, and the UI needs change notifications, which `Flow` gives for free from Room.

### Room 3 with the platform SQLite driver
Room 3.0.1 (KSP), entity `ProductEntity`, `ProductDao`, `CustomNotifierDatabase` (version 1, `exportSchema = true`, schema JSON committed under `app/schemas/` through the Room Gradle plugin). The database is built with `AndroidSQLiteDriver` (framework SQLite) rather than `BundledSQLiteDriver`, which would ship a native SQLite in the APK (ADR 0010). No `fallbackToDestructiveMigration`: a missing migration must fail loudly, never drop user data. All queries are Room DAO queries, which are parameterized (ADR 0006).

The adapter (`RoomProductRepository`) maps entity to domain and back in one place; domain validation runs on read, so a corrupted row fails loudly instead of producing an invalid product.

### Column mapping
| Domain | Column(s) |
|---|---|
| `ProductId` | `id TEXT PRIMARY KEY` (canonical UUID) |
| `ProductName`, `UnitLabel` | `name TEXT`, `unit_label TEXT` |
| `PackageSize` | `package_size INTEGER` |
| `ConsumptionRate` | `rate_units INTEGER`, `rate_days INTEGER` |
| `Stock.units` (`Quantity`) | `stock_numerator TEXT`, `stock_denominator TEXT` (decimal `BigInteger`) |
| `Stock.recordedAt` | `recorded_at_epoch_second INTEGER`, `recorded_at_nano INTEGER` |
| `Rule.leadTime` | `lead_time_days INTEGER` |

`Quantity` needs a way to expose and rebuild its numerator and denominator; the executor adds the narrowest public API for that (for example `numerator`/`denominator` properties and the existing `of(numerator, denominator)` factory). Ordering for `observeAll` (`ORDER BY name COLLATE NOCASE, id`) is done in SQL. SQLite's `NOCASE` folds ASCII only; acceptable for the MVP and noted below.

### Manual dependency injection (ADR 0015)
A `CustomNotifierApplication` (declared in the manifest) creates one `AppContainer` that lazily builds the database and exposes `productRepository: ProductRepository`. Later changes add to it (`Clock`, `ZoneId` provider, scheduler). ViewModels get dependencies through a factory reading the container.

Alternatives considered: Hilt (annotation processing, a Gradle plugin and generated code, heavy for one database and a handful of classes) and Koin (runtime resolution, errors at run time instead of compile time). Rejected for the MVP; ADR 0015 records the decision and when to revisit it (when the container becomes hard to maintain by hand).

### Tests
Robolectric JVM tests in `:app` against a real Room database:
- An in-memory database for round trip, replace, delete, unknown identity, ordering and the observation sequence (`kotlinx-coroutines-test`; observation collected with a test scope).
- A file database that is closed and reopened, to cover "survive a restart" (a new database instance over the same file stands in for a new process).
- Domain tests for `ProductId` (kept through every operation, unique on identical values).

## Risks / Trade-offs

- [KSP version must match Kotlin 2.4.20 and AGP 9.4.1] → The executor picks the matching KSP release and records it in the catalog; if none is compatible, stop and escalate (no workaround).
- [`NOCASE` ordering is ASCII-only: "Ábaco" sorts after "Zinc"] → Acceptable until the Spanish translation (`#48`); then sort in the domain with a `Collator` if the owner wants it.
- [Robolectric's SQLite may differ from a device's] → Room runs the same generated SQL; the E2E suite will exercise the real database once the UI exists (`#42`).
- [`Product` constructor and `Product.create` change again (new `id`)] → Only tests call them; persisted data does not exist yet.
